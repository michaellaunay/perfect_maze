# Multi-level mazes (design)

!!! note "Status"
    This page is a **design proposal**. Nothing described here is implemented
    yet; it exists so the design can be reviewed before any code is written.

## Goal

Build a *tower* of stacked mazes:

- each level is an ordinary 2D **perfect** maze, built independently, and
  levels may have **different sizes**;
- each level is **placed freely** above the one below it: its top-left
  corner is offset by `(dx, dy)` cells from the corner of the level below;
- a chosen number of cells of each level communicate with the level below
  through **stairs**, so the whole tower can be walked from any level to any
  other;
- the parameters (number of levels, size, offset and number of stairs of
  each level) are asked **before** generation, then every level is rendered
  with the stair cells marked `U` (up), `D` (down) or `B` (both).

## Vocabulary

| Term | Meaning |
| --- | --- |
| **Level** | One 2D perfect maze. Levels are numbered from `0` (ground) upwards. Each level has a width, a height and an **origin**. |
| **Offset** | `(dx, dy)`: position of the top-left corner of level `i` relative to the top-left corner of level `i − 1`. May be negative. Level `0` has no offset. |
| **Origin** | Absolute position of a level's top-left corner in the tower: the sum of the offsets of the levels up to it. Level `0` is at `(0, 0)`. |
| **Tower coordinates** | Absolute cell coordinates `(X, Y)`. Cell `(x, y)` of level `i` with origin `(ox, oy)` is at `(X, Y) = (ox + x, oy + y)`. |
| **Overlap** | The cells of two consecutive levels that have the same tower coordinates: the intersection of the two rectangles. Stairs can only be placed there. |
| **Stair** | A passage between the cell of level `i` and the cell of level `i + 1` that share the tower coordinates `(X, Y)`. |
| **Tower** | The list of levels plus the list of stairs. |

## Parameters and prompts

The interactive session asks, in order:

1. the number of levels `n ≥ 1`;
2. for level `0`: its width and height;
3. for each level `i ≥ 1`: its width, its height, its offset `dx, dy` from
   the level below, then the number of stairs `k_i` between level `i` and
   level `i − 1`.

Validation happens as each value is typed and re-prompts on error:

- widths and heights are integers `≥ 1`;
- `dx, dy` are two integers, possibly negative, separated by a comma or a
  space; the resulting overlap with the level below must contain at least
  one cell, otherwise the offset is refused with the allowed range;
- `k_i` is an integer with `1 ≤ k_i ≤ overlap(i − 1, i)`; the prompt shows
  the maximum, e.g. `Stairs down to level 0 (1-15) [1]:`.

A default is offered in brackets (`0, 0` for the offset) and accepted with an
empty line, so a tower can be created by pressing Enter repeatedly. Only once
every value is known is the tower generated and printed.

The same parameters can be passed on the command line for scripts and tests,
one level per argument, in the form `WIDTHxHEIGHT[@DX,DY][:STAIRS]`:

```shell
perfect-maze levels 8x5 6x4@1,1:2 4x3@-1,2:1 --seed 7
```

## Structure and properties

Every level is generated by the existing [`build_maze`][perfect_maze.maze.build_maze],
so each level is a perfect maze on its own: `w·h − 1` passages, connected,
no loop. Stairs are then added without changing any wall.

**With exactly one stair per pair of levels, the whole tower is itself a
perfect maze** (a tree connected to a tree by a single edge is a tree).

**With `k ≥ 2` stairs between two levels, the tower contains loops**: two
trees joined by `k` edges have `k − 1` independent cycles. Each level stays
perfect in 2D, which is what was asked, but a path between two cells of the
tower is no longer unique. This is a deliberate choice; a future
`--globally-perfect` option could restore uniqueness by closing one 2D wall
per extra stair, at the cost of breaking the 2D perfection of a level, so it
is not part of this design.

Stairs are chosen uniformly at random among the overlap cells of the pair,
without replacement, and stored in tower coordinates. A cell can be the top
of a stair to the level below *and* the bottom of a stair to the level above;
it is then marked `B`.

Generation is reproducible with `--seed`, and the recording feature
(`--output`) stores, for each level, its size, offset and `open_walls`, plus
the list of stairs, so a tower can be rebuilt exactly.

## Rendering

The compact renderer used for 2D mazes gives each cell two columns and one
line: a corner glyph and the cell's north wall. The vertical walls are
carried by the corner glyphs, so **there is no free character per cell**
where a marker could go. Multi-level towers therefore use a *wide* style:
two lines per cell, one for the north walls and corners, one for the west
walls and the cell interior. The interior is three columns wide so cells
look roughly square in a monospace font, and the marker sits in the middle.

The corner glyphs come from the same 16-entry table as the compact renderer,
so the two styles are consistent, and the wide style will also be offered
for plain 2D mazes (`--style wide`).

Markers: `U` — a stair goes up to level `i + 1`; `D` — a stair goes down to
level `i − 1`; `B` — both.

Levels are printed from the ground up, each with a heading giving its index,
its size, its offset from the level below and its number of stairs. Because
levels are offset, each drawing is **shifted on screen by its origin** (four
columns per cell horizontally, two lines per cell vertically, relative to
the left-most and top-most origin of the tower), so that a `U` and the `D`
facing it are printed in the same column and at the same distance from the
top of their drawings. This makes stairs easy to match by eye; a
`--no-align` option prints every level flush left.

Example, seed 7, `8x5 6x4@1,1:2 4x3@-1,2:1`:

```text
Level 0 (8x5) — ground
┌───────────────┬───┬───────────┐
│               │   │           │
│   ╶───┐   ╷   │   ╵   ┌───────┤
│       │ U │   │       │       │
│   ╷   ├───┘   ├───╴   ╵   ┌───┤
│   │   │       │           │   │
├───┴───┘   ┌───┤   ╶───┐   │   │
│         U │   │       │   │   │
│   ╶───┐   ╵   ╵   ╷   └───┘   │
│       │           │           │
└───────┴───────────┴───────────┘

Level 1 (6x4) — offset (+1, +1) from level 0, 2 stair(s) down


    ┌───────────────┬───────┐
    │     D         │       │
    │   ┌───────┬───┘   ╶───┤
    │   │       │           │
    │   ╵   ╶───┘   ╷   ╷   │
    │     D   U     │   │   │
    │   ╶───┐   ╷   ├───┘   │
    │       │   │   │       │
    └───────┴───┴───┴───────┘

Level 2 (4x3) — offset (-1, +2) from level 1, 1 stair(s) down






┌───────────────┐
│             D │
│   ╷   ╶───┬───┤
│   │       │   │
│   ├───╴   ╵   │

```

Level 1 is offset by one cell to the right and one down from level 0; level 2
is one cell to the left and two down from level 1, hence back at column 0 and
three cells down from the ground. The `D` at the top right of level 2 faces
the `U` of level 1 immediately above it on screen.

## API sketch

```python
from perfect_maze import Cell, Maze


class LevelCell(Cell):
    """A cell that may hold a stair."""

    __slots__ = ("up", "down")
    up: bool  # stair to the level above
    down: bool  # stair to the level below


@dataclass(frozen=True)
class LevelSpec:
    width: int
    height: int
    offset: tuple[int, int] = (0, 0)  # from the level below; ignored for level 0
    stairs: int = 0  # to the level below; ignored for level 0


@dataclass
class Tower:
    levels: list[Maze]  # cells are LevelCell
    origins: tuple[tuple[int, int], ...]  # absolute origin of each level
    stairs: tuple[tuple[int, int, int], ...]  # (lower level, X, Y) in tower coordinates

    def __getitem__(self, lxy: tuple[int, int, int]) -> LevelCell: ...
    def overlap(self, lower: int) -> list[tuple[int, int]]: ...
    def neighbours(self, level, cell) -> Iterator[tuple[int, LevelCell]]: ...


def build_tower(
    specs: Sequence[LevelSpec],
    *,
    randrange=random.randrange,
    stairs: Sequence[tuple[int, int, int]] | None = None,
    open_walls: Sequence[Sequence[OpenWall]] | None = None,
) -> Tower: ...


def printable_tower(
    tower: Tower, *, cell_width: int = 3, align: bool = True
) -> str: ...
def printable_maze(
    maze,
    *,
    style: Literal["compact", "wide"] = "compact",
    cell_char: Callable[[Cell], str] | None = None,
) -> str: ...
```

`build_tower` draws, through the same `randrange` callable as the levels, the
stair positions as indexes into the overlap list, so a seeded tower is
reproducible and the recording/replay mechanism extends naturally.

## Command line

The 2D generator keeps its current interface; towers get a sub-command:

```text
$ perfect-maze levels
Number of levels [2]: 3
Level 0 width [6]: 8
Level 0 height [4]: 5
Level 1 width [6]: 6
Level 1 height [4]: 4
Level 1 offset from level 0 (dx, dy) [0, 0]: 1, 1
Stairs down to level 0 (1-15) [1]: 2
Level 2 width [6]: 4
Level 2 height [4]: 3
Level 2 offset from level 1 (dx, dy) [0, 0]: -1, 2
Stairs down to level 1 (1-8) [1]:

Level 0 (8x5) — ground
...
```

Options: `--seed N`, `--output PATH` (recording), `--quiet`, `--no-align`,
and the positional `WIDTHxHEIGHT[@DX,DY][:STAIRS]` specs which skip the
prompts. When standard input is not a terminal and no spec is given, the
command fails with a usage error rather than waiting for input.

## Tests

- Each level of a generated tower is perfect (reuse the 2D property test).
- Origins are the cumulative sums of the offsets; `overlap()` is the exact
  rectangle intersection, including with negative offsets and with a level
  entirely inside or larger than the one below.
- Exactly `k_i` stairs between levels `i − 1` and `i`, all inside the
  overlap, no duplicate; an offset leaving no overlap is rejected.
- `up`/`down` flags match the stair list; a `B` cell has both.
- A tower with all `k_i = 1` is globally perfect (BFS over levels, `n − 1`
  passages in total); a tower with some `k_i ≥ 2` is connected and has
  exactly `Σ (k_i − 1)` extra passages.
- Same seed ⇒ same tower; a recorded tower rebuilds identically.
- Wide renderer: dimensions `(cell_width + 1)·w + 1` columns by `2h + 1`
  lines, markers at the expected positions, fixtures for a small tower.
- Aligned rendering: a `U` and its `D` are on the same column and at the
  same line offset from the top of their level, for positive and negative
  offsets.
- Spec parsing (`8x5`, `6x4@1,1:2`, `4x3@-1,2`, errors) and prompts driven
  by a scripted `input()`, including re-prompt on invalid values, on an
  offset without overlap, and the `k` upper bound.

## Patch plan

1. `feat(render)`: wide style and `cell_char` hook for `printable_maze`,
   with fixtures. Independent of towers, usable on its own.
2. `feat(tower)`: `LevelCell`, `LevelSpec` (with offset), `Tower` with
   origins and `overlap()`, `build_tower`, tests of structure and
   reproducibility.
3. `feat(render)`: `printable_tower` with aligned and flush-left output.
4. `feat(cli)`: `perfect-maze levels` sub-command, prompts (including the
   offset), spec parsing, recording.
5. `docs`: turn this page into user documentation; changelog `1.1.0`.

## Open questions

1. Display order: ground level first (as above) or top level first?
2. Should a stair cell be allowed to be `B`, or should the two pairs draw from
   disjoint cells? (`B` is allowed in this design.)
3. Interior width of the wide style: 3 columns (proposed) or 1 for very
   large levels?
4. Offsets are relative to the level below, as requested. Should the
   recording file also store absolute origins for convenience?
5. Naming: *tower*, *levels* and *stairs* are used here; *floors* and
   *ladders* are alternatives.
